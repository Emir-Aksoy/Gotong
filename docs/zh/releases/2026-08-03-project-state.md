## 这是什么项目

**Gotong**(词源马来语 *gotong-royong*,「众人协力」)是一个开源的「人 - 智能体 - 机构」
协作框架。三条从 v0 到今天没变过的立场(详见 [`../../CHARTER.md`](../../CHARTER.md)):

1. **框架不跑 LLM**——hub 只路由消息、派任务、写 transcript、发事件,决策权永远在
   参与者(agent / 人 / 外部服务)手里。
2. **人和 agent 是同一个 `Participant` 抽象**——不存在「人是特权角色,agent 是工具」
   这种二等设计,一切协作走同一套消息 + 任务 + transcript。
3. **状态都是磁盘文件**——`.gotong/` 目录里能看到 transcript / agents / sessions /
   secrets / vault。复制目录就是搬走整个房间,重启对参与者透明。

围绕这三条,项目分三层目标:① 一个人 + 自己的 AI(「我的 AI 桌面」,5 分钟跑起来、
不写代码);② 人 / agent 跨组织协作(凭证 / 数据 / 计费各自归属,不共享中央节点);
③ 框架本身要清晰、稳定、跟得上 AI 的发展速度。

## 项目规模(结构性事实)

- **37 个包**,pnpm workspace,依赖方向单向(`protocol` 零依赖 → `core` → `workflow` /
  `inbox` → 各能力包 → `host` 装配层),其中 36 个 `@gotong/*` scoped 包已在 npm 全部
  公开发布,另有一个 PyPI 上的 Python SDK。
- **116 个 `GOTONG_*` 环境旋钮**,登记在案且「冻结」——新增一个必须显式登记进
  `scripts/gotong-env-registry.txt`,否则承重门直接变红。绝大多数能力默认关闭
  (未配置 = 与今天字节完全一致),只有配置了才会分叉行为。
- **四道结构性护栏**持续跑绿(`pnpm check:guards`):内核依赖方向不倒转、环境旋钮
  不无声膨胀、装配层(如 `host/src/main.ts`)行数只降不升的棘轮、版本号一致性。
  这四道门存在的理由:功能一直在加,但「装配层越堆越重、旋钮越加越多」这个
  反模式必须有代码而不是自觉去挡住。详见 [`../CONVENTIONS.md`](../CONVENTIONS.md)。
- 测试覆盖到什么程度不追求在这里给一个会很快过期的总数字,但持续遵守的纪律是:
  **每个新能力配对应回归测试,四道护栏门必须全绿才算收工**——这条纪律在最近
  一次实际验证中(2026-08-02,面板写卡功能)是 host 包 2677+ 测试全绿、四门 PASS。

## 三层北极星,现在做到哪一步

### 第一层:我的 AI 桌面(个人常驻管家「阿同 / Atong」)

这是投入最密集的一层,一个反应式的、有工具循环的常驻 agent,已经不只是「能聊天」:

- **记忆**——分层记忆 + 睡眠期后台蒸馏 + 原子事实抽取 + 融合召回(关键词⊕本地
  向量,零外部依赖默认开)+ 可选联想图谱/陈旧校正/外部 embedder/git 快照(全部
  opt-in,未开不影响任何人)。
- **对话连续性**——每成员滚动会话窗,同一个人在飞书聊一半、切到网页接着聊,
  阿同不会「失忆到上一句在等什么」。
- **任务笔记本**——阿同自己维护一份跨会话的任务台账,卡壳会零 LLM 提醒,不会
  把长任务的进度弄丢在某一轮对话里。
- **五感**——时钟感知、待办审批提醒、对话间隔感知、语言偏好、来源渠道感知、
  能力自我介绍、hub 健康感知、好友信任分档感知、自我状态一览、定时任务/成员
  名录只读投影。这些全部零 LLM(纯拼字符串或纯投影),专为弱模型也能稳当地
  知道「当下」而设计。
- **多模态**——语音回复(TTS)、语音转写(ASR)、看图(VIS)三只眼睛全部经由
  同一 MiMo 模型通道打开,红线是**只接厂商官方系统音色,绝不模仿真人声音**。
- **可配置面板 + Web Push**——面板由 JSON 配置驱动(SDUI),阿同能在获得授权的
  范围内帮成员调整自己的面板布局、把查到的天气/资讯整理写进本人可见的展示卡;
  纯网页用户也能收到桌面推送提醒,自研实现了 RFC 8291/8292(零外部依赖)。
- **自愈**——生产环境有独立于 hub 进程之外的看门狗,每分钟探活,连续判定「卡死」
  才会拉起重启,并把每次自愈事件如实记进台账、按需播报给成员。这套机制已经在
  真实故障注入演练(SIGSTOP 冻结进程)中验证过完整闭环。
- **原生独立客户端(壳 app)**——iOS + Android 双端已经建完到「装上能用、真机
  验证过完整配对/使用动线」的程度,但**这个方向在 2026-08-02 被显式搁置**:
  用户在真机上对比大陆成熟消费级 App 后判定观感差距过大,诊断出真正的差距
  主要在「数据是否真的活起来」和「视觉资产投入」,而不是配置驱动这个范式本身
  (大陆头部 App 内部用的正是同一套思路)。壳工程代码原样留在仓库,恢复路径
  写在 [`../APP-SHELL.md`](../APP-SHELL.md) 顶部;**网页端的可配置面板不受影响,
  在生产环境持续服役**。

### 第二层:跨组织协作(联邦 / 跨 hub)

- **联邦 mesh**——hub 之间可以握手互联,支持分级信任(未知 / 令牌握手 / owner
  签名确认 / owner 显式提升四档),信任只能降低审批摩擦,永远不能自动突破底线,
  且「声明的信任档位」与「真正被信任的档位」结构性分离,不能靠自报升级。
- **标准对齐**——对外的 agent 名片支持可选的数字签名(A2A v1.0 规范,ES256 +
  JWKS),消费方可以做「锚定公钥指纹」的独立校验,防止被伪造的 JWKS 欺骗。
- **管家出网**——阿同能代表成员向已经建立信任边的对端 hub 求助(问答式跨
  hub 协作),但这条通道完全复用既有的审批闸,不会绕过任何一层已有的授权。
- **真实两进程跨 hub 测试机制**——不是同进程模拟,是真的起两个独立生产
  二进制互联,覆盖同一台机器 / 跨两台 VPS / 本地电脑连 VPS 三种真实拓扑,
  在建这套机制的过程中实际抓到并修复了两个此前从未被发现的生产级 bug
  (共享端口握手互相干扰、重连后参与者泄漏)。

### 第三层:框架本身

- **护栏与文档金字塔**——防止装配层再次膨胀的四道结构性门(见上);文档从
  「110+ 篇账本平铺在一起」重排成六级金字塔(从「这里开始」到「出处/历史」),
  历史深潜账本移进独立的 `docs/zh/ledger/` 归档层。
- **5 分钟上手漏斗**——`QUICKSTART.md` + 一个真的会跑红灯的「首个结果」验收门
  (`pnpm check:first-result`),不是一份没人验证过的说明文档。
- **模型路由与调用韧性**——多候选自动 failover + 熔断 + 手动测试通道健康 +
  per-candidate 独立凭证(今天生产环境正在用它做「主力模型 + 备用模型」的双厂商
  编排);Anthropic 请求路径的原生提示词缓存也已经打开,显著降低重复对话的成本。
- **接入现实生活**——通过标准 MCP 协议接入 Notion / Todoist(静态令牌)、
  Google 日历与邮箱(完整 OAuth2 出站流程,令牌进金库加密、自动保活刷新)——
  框架本身依旧不存任何用户数据,一律只读投影 + 审批闸控制「谁能替你动」。
  同时新增了微信(官方 iLink 协议)作为第七条 IM 接入通道。
- **场景样板**——一人公司旗舰样板、专业服务公司(多人+多 agent+企业数据/知识库
  只读接入)样板、奶茶店/酒吧门店运营样板、家庭 hub 样板(审批签发 + 家庭晨报),
  全部可以在模板画廊里一键安装体验,而不需要从零手写配置。

## 生产环境现状

项目维护者本人有一套长期在跑的生产实例,部署在其私有云 VPS 上(具体主机信息不
适合放进公开仓库,故此处只写能力现状):

- 常驻由 systemd 托管,配了独立于主进程之外的自愈看门狗,近期已经过真实故障
  演练验证。
- 通过飞书(Lark)与真实成员对话,近期把主力大模型通道从一家即将到期的服务商
  切换到了另一家(仍保留原服务商作为故障转移的备用通道,不是直接下线),语音/
  听觉/视觉三条多模态通道也已经在生产打开并验证过真实调用链路。
- 一个面向「菜园顾问」场景的可配置面板样例已经装好并在真机(Android)上验证过
  完整配对与使用动线,当前还差两件事才算真正「活起来」:成员本人还没有通过
  聊天开启带外部数据整理的晨报订阅(这是一个只有本人能点头的同意面,任何人都
  不能替他打开);面板里的示例作物名还是占位数据,等真实作物信息到位后会替换。

## 已知缺口 / 下一步

- **壳 app 方向已搁置**,不是放弃,是等数据活水与视觉资产投入到位再重新评估——
  详见 [`../APP-SHELL.md`](../APP-SHELL.md) 顶部的搁置声明。

  这是壳 app 方向恢复时的第一步,但当前不催不推进。
- **家庭 hub 场景样板**还没有真实试点家庭验证「非技术家长 15 分钟开箱」的
  假设是否成立。
- **视觉资产层**(图标/插画等设计投入)被诊断为壳 app 观感差距的真实组成部分,
  是壳 app 方向重启后的优先投入项,但目前还没有立项。
- 一些功能已经写完但**处于「等本人一个动作」的休眠态**——比如生产环境的
  晨报数据整理需要成员本人在聊天里开口打开(设计上就不允许被代开)。这类
  「代码已就绪、真实使用尚未激活」的情况,不算工程缺口,但值得在这里如实记录。
