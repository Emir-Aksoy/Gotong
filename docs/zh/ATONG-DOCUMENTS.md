# 阿同生成 PPT 和 Word

> 状态：**已实现（2026-11-01），未部署**。真实飞书发送和真实 Office / WPS 显示都还没验证，见第六节。
> 方向：**T**（工具调用能力）。第一版只发飞书，不依赖 HANDS。

---

## 一、一句话

阿同提交结构化内容，服务端确定性地生成 `.pptx` / `.docx`，发到成员本人的飞书私聊。

模型不写代码，也拿不到文件系统。它能决定的只有内容和三种配色之一，版式由代码决定。

## 二、工具

只有一个一等工具 `write_document`，schema 估算约 **490 tokens**（上限 600，由测试守住）。

| 用法 | 参数 |
|---|---|
| 一次成稿 | `format`、`title`、`sections`、`finish: true` |
| 分批：新建 | `format`、`title`、`sections` → 返回 `draft_id` |
| 分批：追加 | `draft_id`、`sections` |
| 分批：发送 | `draft_id`、`finish: true` |

一节可以有 `heading`、`paragraphs`、`bullets`、`table`、`chart`、`notes`。

**schema 里没有收件人字段**，文件只能发给发起任务的成员本人。

校验是宽进严出：数字形式的标题、系列名会转成文字；不认识的字段（章节、表格、图表、系列每一层都查）和其他类型的值（包括布尔值，`title: false` 不会变成叫 false 的文档）一律拒绝，不会收下再悄悄丢掉。表头和单元格是例外：`true` 按文字保留，因为它可能就是数据。

分批是为了防单次输出撞上限：30 页一次写完容易撞模型输出上限或上游断流，分批后草稿在盘上，重启不丢。模型重试时把上一批原样再传一遍，不会追加两次。

## 三、数据路径

```
阿同 → write_document → 草稿 JSON（<空间>/butler/documents/user/<userId>/）
                            ↓ finish
                       一次性子进程生成 → ButlerReachableRegistry.pushFile → 飞书私聊
```

- **草稿**：原子写。最多 5 份未完成，超出时清掉最旧的并明说；7 天没改动就清掉。清理发生在该成员下次调用工具时，成员不再调用就一直留在盘上。
- **成品不留盘**：只在内存里走一遍。发送成功后删除草稿，只留一个标记防止重复发送，标记里只有草稿 ID 和发送时间，没有标题和正文。
- **不走推送闸门和 outbox**：这是成员当面要的文件，不是后台推送。
- **发送前核对绑定**：可达表记的是成员上次从哪说话，解绑和换绑都不会更新它，重启后还在。文件发出去收不回来，所以探测和发送前都查一次这个账号现在绑给谁，对不上或查询失败都不发，按「还没绑定」处理。后台文字推送共用这个核对。
- **飞书**：`im/v1/files` 上传后发 `msg_type: file`。其他 IM 桥没有 `sendFile`，会如实报告不支持。

## 四、版面

规划器是纯函数，按中文字宽估算换行。固定行距加零内边距让估算不依赖字体度量。

- 正文字号 20→16，表格 14→12，放不下就**拆页，绝不删字**。
- 续页标题加「（续）」，表头每页重复，超过一页高的表格行也会拆开。
- PPT 用原生表格和原生图表，可以在 PowerPoint 里继续编辑。
- Word 没有原生图表，转成数据表格，并告诉模型。PPT 的备注在 Word 里变成段落，第一行带「备注:」，内容不丢。
- 字体写 `Microsoft YaHei`，东亚字符用 `<a:ea>` 单独指定。图表文字例外：库只写 `<a:latin>`，中文回落到系统字体。

## 五、上限和隔离

### 上限

超限一律明确拒绝，这批不保存，不静默截断。

| 项 | 上限 | 为什么 |
|---|---|---|
| 内容块（段内每一行、单元格等） | 8000 | 见下 |
| 草稿大小 | 1MB | 防长文本 |
| PPT 页数 | 120 | 拆页之后算 |
| 章节 | 300 | |
| 每张表 | 12 列、300 行 | |
| 图表 | 50 个标签、8 组系列；标签和系列名 60 字，标题 200 字 | 图表放不下长文字，也防止绕过字节估算 |
| 成品 | 30MB | 飞书接口上限 |

**内存跟对象个数走，不跟字节走。** docx 给每个段落和单元格建一棵对象树，所以单靠字节上限挡不住：6.7 万字节的短单元格（1.6 万个）会撑爆 192MB 堆，100 万字节的长段落不到 70MB。Word 把段内每一行拆成独立段落，所以按行数算，不按段数：30 万字节、6 万行的文字只要十五段，同样会撑爆。内容块上限取最后一次能生成的 1.2 万个再留余量，由测试在真堆上限里守住。

万一仍然撑爆，子进程被 V8 终止，工具报「内存不够，可以拆成两份」，草稿保留。stderr 只进日志，不进给模型的文案。

### 隔离

第三方库只在一次性子进程里加载，源码扫描门守住这一点：

- 环境变量从零开始（拿不到 hub 的 key），堆上限 192MB，30 秒超时后 `SIGKILL`。
- 全进程同一时刻只跑一个，输出限大小并校验 zip 文件头。

**这不是沙箱**：子进程和 hub 同一用户，文件系统仍可读。它防的是资源失控和环境变量外泄；模型代码本来就不进这里，输入只有校验过的结构化内容。

### 实测内存

构建产物、本机 arm64、Node 20，不是生产的 x86_64 + Node 22。

| 场景 | 峰值 | 成品 |
|---|---|---|
| 31 页 PPT（要点、表格、图表交替） | 84MB | 176KB |
| 40 节 Word | 107MB | 16KB |
| Word，上限处单列长单元格（1MB） | 212MB | 31KB |
| Word，上限处长单元格（980KB） | 208MB | 28KB |
| Word，上限处短单元格 | 198MB | 24KB |
| Word，17 个最大图表 | 197MB | 31KB |
| Word，上限处全是段内换行的要点 | 155MB | 15KB |
| PPT，上限处短单元格（37 页） | 143MB | 230KB |
| PPT，119 页小图表 | 129MB | 1MB |

同一批上限形状在本机 Node 22（arm64）上也都能生成，峰值略高，最高约 225MB。x86_64 还没测，见第七节第 4 步。

用完进程退出，内存全部归还。主进程不加载这两个库。

## 六、已验证和未验证

| 项 | 状态 | 依据 |
|---|---|---|
| 文件结构 | 已验证 | `python-pptx` / `python-docx` 独立打开，页数、文字、原生图表、表格都对 |
| XML 合法 | 已验证 | 严格解析全部部件，含图表内嵌的工作簿 |
| 封面、要点、表格、长文本、分隔页显示 | 已验证 | Quick Look 看过，三种配色无溢出、无方块字 |
| 图表内容显示 | 部分验证 | 图表 XML 装进 `python-pptx` 的包后，Quick Look 画对了中文标题、数据和图例 |
| 图表在 PPT 整页里的显示 | **未验证** | Quick Look 画不出 pptxgenjs 的任何图表，连它的默认样例也是空白 |
| PowerPoint / WPS / Word 实际显示 | **未验证** | 本机没有，字体也和 Windows 不同 |
| PPT 备注里的换行 | **未验证** | 字一个不少，但库只接受一段字符串，换行留在同一段里，真软件里可能连成一行 |
| 真实飞书发送 | **未验证** | 后台权限已确认，但不碰生产凭证，实际发送只用假接口断言过请求形状 |

用 Quick Look 抽查时要注意它的四个偏差，都用对照样本确认过，不是生成器独有的：只缩略第一页；项目符号画到左边距外；忽略 Word 表格声明的宽度；不写符号颜色时一律画黑点（深色主题上几乎看不见，库也不支持设置，部署后要在真软件里确认会跟随文字色）。

## 七、下次部署要做的

1. `pnpm install`：新依赖 `pptxgenjs`、`docx`，约 25MB。根 `overrides` 把 `image-size` 抬到 2.x：`pptxgenjs` 声明依赖它，但构建产物根本不加载（相关代码已注释掉），我们也不接受图片，抬版本只是为了消掉高危告警。`docx` 依赖的 `nanoid@6` 声明要 Node 22 以上，生产的 Node 22 满足；本机 Node 20 也跑通了全部测试，但这不在它声明的支持范围内。
2. 飞书权限：2026-11-01 在开发者后台确认，`im:resource`（相关接口含「上传文件」）、`im:message:send_as_bot` 都已开通，且无待发布的修改。部署时核对生产用的确实是这个应用。
3. 成员发一次「做个三页 PPT，带一张图表」，在 PowerPoint 或 WPS 里看图表和字体。
4. 在服务器上用构建产物复测第五节的上限场景，确认 x86_64 + Node 22 下不会撑爆堆。

## 八、代码地图

| 文件（`packages/host/src/`） | 职责 |
|---|---|
| `personal-butler-documents.ts` | 工具本体：草稿、上限、发送、失败文案 |
| `butler-document-spec.ts` | 类型、上限、校验、内容块计数 |
| `butler-document-layout.ts` | 纯版面规划器 |
| `butler-document-render.ts` | 唯一 import 第三方库的模块 |
| `butler-document-worker.ts` / `butler-document-runner.ts` | 子进程入口 / 启动和队列 |
| `butler-reachable.ts` | `canPushFile` / `pushFile`，只走私聊路由，投递前核对绑定（文字推送共用） |

飞书侧在 `packages/im-lark/src/bridge.ts`，接口是 `packages/im-adapter/src/types.ts` 里可选的 `ImBridge.sendFile`。
